# ADR-005 — 모놀리스 + 도메인 수직 슬라이스

| | |
|:---|:---|
| 상태 | 채택 |
| 시기 | 2026-07 (아키텍처 설계 단계) |

## 맥락

Application Architecture에는 9개의 논리 모듈이 있습니다. 3인 팀 · 단일 EC2 환경에서 이것을 몇 개의 배포 단위로 나눌지 정해야 했습니다.

## 결정

**모듈형 단일 앱(모놀리스)** 으로 만든다. 아키텍처 다이어그램 범례에 그대로 명시했습니다 — *"모듈 경계는 논리적 책임을 나타내며 독립 배포 단위를 의미하지 않음."* 대신 코드 안에서 경계를 지킨다:

- 패키지는 기술 레이어가 아니라 **도메인 단위 수직 슬라이스**(13개). 각 도메인이 controller부터 repository까지 자기 것을 소유한다.
- **최상위 `infrastructure` 패키지는 없다.** 외부 시스템 어댑터는 그것을 쓰는 도메인 안에 산다 — 모든 벤더 클래스를 한 바구니에 모으면 각 도메인이 둘로 쪼개지기 때문.
- 예외는 진짜 비동기 경계뿐 — 임베딩 Lambda는 실행 환경(Python·GPU/메모리 프로파일)이 달라 물리적으로 분리했다.

## 근거

3인 팀에서 서비스 분리는 배포·관측·계약 관리 비용을 곱절로 만들 뿐 이점이 없습니다. 반면 도메인 경계를 코드 수준에서 강제해 두면, 나중에 특정 도메인을 떼어낼 때 경계가 이미 그어져 있습니다.

## 결과

- 도메인 간 참조가 명시적이라 의존 그래프를 소스에서 자동 추출할 수 있게 되었습니다 ([백엔드 문서](../tech/server.md)의 도메인 의존 다이어그램).
- 레이어·패키지 규칙은 저장소의 규칙 문서 12종으로 관리되어 사람과 AI 도구가 같은 컨벤션을 따릅니다.
- 사진 도메인이 커지면서 `embedding` `cluster` `folder` `selection` `collab` `trash`가 `photo`의 하위가 아닌 **동급 도메인**으로 분리되었습니다 — "합치면 photo가 모든 것이 떨어지는 패키지가 된다"는 규칙의 실제 적용입니다.
