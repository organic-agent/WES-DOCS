# ADR-001 — 이미지 바이트는 앱 서버를 지나지 않는다

| | |
|:---|:---|
| 상태 | 채택 |
| 시기 | 2026-07 (Upload PoC 직후, 본 개발 전) |

## 맥락

웨딩 촬영 한 건의 원본은 수천 장, 장당 수-수십 MB다. 업로드가 앱 서버를 경유하면 단일 EC2(t4g.micro)의 네트워크·메모리가 곧바로 병목이 되므로, 서버 스케일이 업로드 트래픽에 끌려다니게 된다.

## 결정

서버는 **presigned URL 발급과 상태 관리만** 한다. 업로드는 3단계 — ① 서버가 presigned PUT URL 발급 ② 브라우저가 S3에 직접 업로드 ③ 브라우저가 서버에 완료 통지. 다운로드·열람도 presigned GET으로 브라우저가 S3에서 직접 받는다.

## 근거

본 개발 전 [Upload PoC](../tech/poc.md)에서 동일한 20GiB 데이터셋(약 4,096장)으로 두 경로 — 개별 presigned PUT vs ZIP multipart 업로드 후 서버 해제 — 를 비교했다. 개별 PUT은 파일 단위 재시도와 진행률 표시가 자연스럽고, 업로드 즉시 파일별로 쓸 수 있고, 서버가 바이트를 전혀 만지지 않는다. ZIP 경로는 전송 후 서버가 받아 해제해 재업로드하는 동안 서버 부담과 대기가 생긴다.

## 결과

- 업로드 처리량이 앱 서버 사양과 분리됐다. 프론트엔드는 파일별 진행률·실패·재시도를 독립적으로 처리한다.
- URL만 발급되고 실제 객체가 없는 상태가 존재하므로 사진 상태 머신에 `PENDING`이 필요해졌다.
