# ADR-004 — 벡터 저장은 pgvector, 클러스터링은 Union-Find

| | |
|:---|:---|
| 상태 | 채택 |
| 시기 | 2026-08 (Cycle 2, 임베딩 파이프라인 구축) |

## 맥락

유사 사진 스택을 만들려면 사진당 임베딩 벡터(768차원)를 저장하고 유사도를 조회할 저장소가 필요하다. 선택지는 전용 벡터 DB(별도 인프라), 외부 관리형 서비스, 기존 RDS PostgreSQL의 확장 세 가지였다.

## 결정

**pgvector 확장을 쓴다** — 사진 메타데이터와 같은 RDS, 같은 `photos` 테이블의 `vector(768)` 컬럼. 클러스터링은 코사인 유사도 임계값 이상의 쌍을 조회한 뒤 **Union-Find 연결 요소**로 묶는다.

## 근거

- 운영 부담 : 폐기 가능한 단일 EC2+RDS 환경에 벡터 DB를 하나 더 세우는 것은 규모에 맞지 않는다. pgvector는 확장 설치가 전부다.
- 데이터 지역성 : 스택 구성은 항상 "같은 갤러리 안"의 조회라서 사진 메타와의 조인이 잦고, 갤러리당 수천 장 규모에서는 인덱스 없이도 충분하다.
- 알고리즘 단순성 : 쌍 → 연결 요소(Union-Find)는 클러스터 수를 미리 정할 필요가 없고(k-means류와 다르다), 슬라이더 레벨별 임계값 변경에 즉시 대응한다.

## 결과

- 로컬·Testcontainers·운영이 모두 동일한 `pgvector/pgvector:pg16` 이미지를 쓰므로 환경 차이가 없다.
- `EMBED_DIM=768`이 DB 컬럼 · 서버 엔티티 상수 · 인프라 설정 **세 곳에서 일치**해야 하는 계약이 됐고, 마이그레이션 규칙 문서에 명시했다.
- 정밀도 보강은 클러스터링 계층에서 해결했다 — 촬영 시각 기반 **시간 조건부 이중 임계값**(연속 촬영엔 관대하게, 먼 사진엔 엄격하게)과 **상호 kNN 필터**(대형 스택의 오염 방지). 상세는 [AI 파이프라인](../tech/ai-pipeline.md) 참고.
