# PoC — 설계를 결정한 두 실험

{: .note }
이 페이지는 당시 실험 조건과 결과를 보존한다. embedder·클러스터 관련 연결은 현재 AI 실행 구조가 아니라 [외부 워커 경계](ai-pipeline.md)를 따른다.

수십 MB짜리 사진 수천 장을 다루는 서비스에서 업로드와 열람을 감으로 설계하면 나중에 뒤집는 비용이 너무 크므로, 본 개발 전에 PoC 두 건으로 **측정하고 결정했다.** 두 실험의 결론이 현재 프로덕션 설계의 근거다.

## 실험 1 — 업로드 : 개별 PUT인가, ZIP인가

*WES-Upload-PoC · 2026-07-10 - 07-11 · LocalStack S3*

약 5MiB 이미지로 구성된 동일한 20GiB 데이터셋(약 4,096장)을 두 경로로 업로드해 속도 · 요청 비용 · 재시도/실패 · 사용 가능 시점을 비교했다.

```mermaid
flowchart LR
    B["React 브라우저"] -->|"세션 생성"| API["Kotlin Spring API"]
    API -->|"presigned URL"| B
    B -->|"경로 1: 개별 PUT ×4096"| S3["S3"]
    B -->|"경로 2: multipart ZIP 1개"| S3
    S3 -->|"ZIP일 때 서버가 받아 해제 후 재업로드"| API
    API --> R["결과 JSON / CSV"]
```

| 비교 축 | 개별 presigned PUT | ZIP + 서버 해제 |
|:---|:---|:---|
| 전송 단위 | 파일별 독립 | 아카이브 1개 (multipart) |
| 실패 시 | 실패한 파일만 재시도 | 아카이브 단위 영향 |
| 사용 가능 시점 | 파일별 즉시 | 서버 해제 완료 후 |
| 서버 부담 | 없음 (바이트 무경유) | 다운로드 + 해제 + 재업로드 |

**개별 presigned PUT을 채택했다.** 파일 단위 재시도·진행률이 되고, 업로드 즉시 파일별로 쓸 수 있고, 서버가 이미지 바이트를 만지지 않으므로 서비스 요구(업로드 진행률 표시, 부분 실패 복구)와 맞다. 이 결정이 지금의 3단계 업로드 파이프라인(발급 → 직접 PUT → 완료 통지)이다. → [ADR-001](../decisions/adr-001-presigned-direct-upload.md)

## 실험 2 — 열람 : 40MB 원본을 어떻게 넘겨볼 것인가

*WES-ImageLoad-PoC · 2026-07-25 - 07-28 · 실제 S3 (CDN 없음) · 82런, 8,200 측정 레코드*

뷰어에서 사진을 연속으로 넘길 때의 로딩 전략을 시나리오(원본 직로드 / 썸네일→원본 / 썸네일→표시용 파생본) × 정책(디바운스 · 프리페치 · 썸네일 선로드) 전 조합으로 측정했다.

### 선명한 이미지가 뜰 때까지

![메인 표시 시간 — 시나리오·정책별]({{ site.baseurl }}/assets/img/poc/chart-main-display.svg){: .poc-chart }

- 40MB 원본을 넘김마다 로드하면 **3.1초** → 이 방식은 성립하지 않는다.
- 표시용 파생본(2048px WebP) 전환만으로 **414ms — 7.5배** 단축.
- 프리페치 1장(디코드 선행)을 더하면 **103ms**, p95는 482→114ms로 안정화. ⇒ 프리페치의 효과는 평균이 아니라 꼬리 지연 제거에서 나온다.

### 넘기는 순간 무언가 보일 때까지

![첫 표시 시간 — 썸네일 선로드 효과]({{ site.baseurl }}/assets/img/poc/chart-first-display.svg){: .poc-chart }

그리드에서 이미 로드된 썸네일을 뷰어가 재사용(선로드)하면 첫 표시가 **21-22ms로 수렴한다.**

### 빠른 연속 넘김 내성 — 디바운스 단독의 함정

![700ms 간격 연속 넘김 완료율]({{ site.baseurl }}/assets/img/poc/chart-completion-700ms.svg){: .poc-chart }

![취소당 낭비 전송 — 디바운스 효과]({{ site.baseurl }}/assets/img/poc/chart-waste-debounce.svg){: .poc-chart }

- 파생본 전환이 원본에서 0%였던 700ms 연타 완료율을 99%로 만든다.
- **디바운스 250ms를 단독 적용하면 완료율이 70%로 떨어진다** — 대기가 시간 예산을 잠식하기 때문이다. 대신 낭비 전송(보여주지도 못할 원본을 받다 버리는 트래픽)은 크게 줄인다.
- 프리페치와 결합하면 완료율 100%를 회복하면서 낭비 절감만 남는다.

⇒ 정책은 단독이 아니라 조합으로 평가해야 한다.

### 남은 병목

![표시용 파생본 로드 단계 분해]({{ site.baseurl }}/assets/img/poc/chart-phase-breakdown.svg){: .poc-chart }

정책을 다 써도 파생본 한 장의 순수 비용은 TTFB 82 + 다운로드 194 + 디코드 113 = **389ms**이고, 지배 항은 네트워크(276ms)다.

⇒ 다음 단축 수단은 클라이언트 정책이 아니라 인프라 — CDN(TTFB)과 AVIF(다운로드)다.

### 최종 채택 조합

**썸네일 선로드 + 표시용 파생본 + 프리페치 1-2장(디코드 선행) + 디바운스 200-300ms.** 이 조합으로 paced 열람 첫 표시 22ms · 파생본 114ms, 700ms 연타 완료율 100%, 낭비 전송 0에 수렴한다. 원본은 줌 진입 시에만 로드한다.

## 실험이 제품에 반영된 것

- **파생본 우선 로딩**이 설계 기반이 됐고, 파생본 생성은 [embedder의 단일 잡](ai-pipeline.md)에 통합했다 — 임베딩을 위해 어차피 디코딩한 이미지를 그대로 JPEG로 인코딩해 저장한다.
- 프론트엔드 그리드는 파생본(`viewUrl`)과 "미리보기 준비 중" 상태를 표시하고, URL 만료 시 재조회한다.
- CDN·AVIF는 측정으로 확인된 후속 과제로 남겨 두었다.

{: .note }
현 구현의 파생본은 임베딩 리사이즈(1024px)를 재사용한 JPEG 단일본(장당 약 200KB)이다. PoC가 권고한 2단 체계(512px 썸네일 + 2048px WebP)는 CDN 도입과 묶어서 진행한다. → [ADR-002](../decisions/adr-002-preview-derivatives.md)
